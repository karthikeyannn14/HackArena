# ID Compatibility Report

## A. Current ID Types
* **Member 1 (MongoDB)**: `ObjectId` (24-character hex strings, e.g., `507f1f77bcf86cd799439011`).
* **Judging Engine (PostgreSQL via Prisma)**: `String` type with `@default(uuid())`.

## B. Cross-Database References
The following entities are inherently cross-system, as they are managed by Member 1 but required by Judging:
* **User** (Mongo) -> referenced by **Judge** (`userId`)
* **Event** (Mongo) -> referenced by **EventJudge**, **AssignmentRun**, **Rubric**, **Project**, **Track**
* **Team** (Mongo) -> referenced by **Project**, **Judge**
* **Project** (Mongo) -> referenced by **Submission**, **Assignment**, **JudgeConflict**
* **Submission** (Mongo) -> referenced in Prisma but technically isolated.

## C. Actual Prisma / PostgreSQL Behavior
In the current `schema.prisma`, ID fields are defined as `String @id @default(uuid())`. 
Because there is no `@db.Uuid` mapping, PostgreSQL stores these fields as standard `TEXT` (or `VARCHAR`). 

**UUID formatting is NOT enforced by PostgreSQL or Prisma for these fields.**
The `uuid()` directive is purely a client-side generator. If a 24-character Mongo `ObjectId` string is explicitly passed during a `prisma.entity.create()` call, Prisma will happily insert it, and PostgreSQL will safely store it as text.

## D. Fields That Are Already Compatible
* All Prisma ID fields (`Event.id`, `Project.id`, `Team.id`, `Judge.userId`) are natively compatible with MongoDB `ObjectId` strings at the column level. 
* A MongoDB string ID can be safely stored anywhere the Judging engine expects a Prisma ID.

## E. Fields That Are Incompatible
* **There is no byte-level or structural incompatibility** with the ID formats themselves.
* **HOWEVER, there is a relational incompatibility.** Because Prisma enforces strict Foreign Key (`@relation`) constraints in PostgreSQL (e.g., `AssignmentRun.eventId` must exist in the `Event` table), the Judging Services currently require actual `Event`, `Project`, and `Team` rows to exist in PostgreSQL. Passing a valid Mongo ID to `generateAssignments` will fail with a Foreign Key Violation if the corresponding "shadow" record hasn't been synchronized into Postgres.

## F. Minimal Schema Changes Required
**None required for ID compatibility.** 
Because `String` maps to `text`, the schema inherently supports storing Mongo IDs. 
To satisfy the strict Foreign Key constraints without rewriting the judging services or dropping relational integrity, the integration architecture simply requires creating **shadow records** (i.e., when Member 1 creates an Event in Mongo, insert a minimal Event record with the exact same Mongo ID into Postgres).

## G. Fields That Must NOT Be Changed
* Do NOT change `String @default(uuid())` to `String @db.Uuid`. Doing so would cause Postgres to rigidly validate UUID v4 format and reject all Mongo ObjectIds.
* Do NOT remove the `@relation` constraints, as the Judging services (like `getEventProjectAggregates`) actively rely on Prisma's relational `include:` joins.

## H. Migration/Data-Loss Risks
Since no schema modifications are necessary for the IDs themselves, there is zero migration or data-loss risk regarding ID data types. The only risk involves ensuring that any newly inserted shadow records precisely mirror the `_id` strings generated by MongoDB.
